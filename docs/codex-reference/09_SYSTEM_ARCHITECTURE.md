# QuoteFlow System Architecture Reference

This document describes the intended architecture of QuoteFlow so Codex can make changes without breaking the design.

## Architecture style

QuoteFlow is a shared-hosting-friendly Laravel monolith.

It is intentionally not a microservice system, not a SPA, and not a queue-worker-heavy application.

Primary style:

```text
Browser
  -> Laravel routes/controllers
  -> Service/business-rule layer where needed
  -> Eloquent models
  -> MySQL/MariaDB
  -> Blade views / redirects / streamed downloads
```

Deployment target:

```text
Exabytes / Plesk shared hosting
LiteSpeed + PHP 8.3
MySQL/MariaDB
Local filesystem storage
File cache/session
Sync queue
Prebuilt CSS
```

## High-level layers

```text
resources/views/*
    Blade UI pages, forms, previews, partials

routes/web.php
    HTTP route map and role middleware

app/Http/Controllers/*
    Request handling, validation, redirect/view orchestration

app/Services/* or app/Support/*
    Business workflow rules, matching rules, payment eligibility,
    verification policies, document numbering, OCR wrappers

app/Models/*
    Eloquent models, relationships, simple display helpers

database/migrations/*
    MySQL/MariaDB-compatible schema

storage/app/*
    Private attachments and generated temp files

public/css/app.css
    Prebuilt Tailwind CSS for shared hosting deployment
```

## Core domain concept: Document

The central aggregate is `App\Models\Document`.

Instead of creating separate tables/controllers for every commercial document, QuoteFlow uses one document model with a `type` field.

Document types:

```text
customer_quotation
customer_po
customer_invoice
purchase_request
supplier_quotation
supplier_po
goods_receipt
supplier_invoice
```

Important related data:

```text
Document
  has many DocumentItem
  has many DocumentBillingStage
  has many Payment
  has many Approval
  has many Attachment
  has many AttachmentExtraction
  belongs to Customer or Supplier
  belongs to related Document through related_document_id
  belongs to creator User
  belongs to approver User
```

## Document lifecycle states

Shared status vocabulary:

```text
draft
pending_approval
approved
rejected
issued
fulfilled
received
matched
part_paid
paid
closed
cancelled
```

Not every status applies to every document type. Any new logic should check both document type and status.

## Customer/outgoing workflow architecture

Intended flow:

```text
Customer Quotation
  -> approval
  -> issue quotation
  -> Customer PO received
  -> accept PO
  -> delivery/service completion
  -> Customer Invoice
  -> issue invoice
  -> receive payment
  -> close
```

Primary document types:

```text
customer_quotation -> customer_po -> customer_invoice
```

Important notes:

- Customer quotations and customer invoices can generate company-facing PDFs.
- Customer PO is normally an uploaded/received customer document, not generated by QuoteFlow.
- Customer invoice payment should only be allowed after the invoice is issued.

## Supplier/incoming workflow architecture

Intended flow:

```text
Purchase Request
  -> approval
  -> Supplier Quotation
  -> Supplier Purchase Order
  -> issue PO
  -> Goods/Service Receipt
  -> Supplier Invoice
  -> invoice verification
  -> invoice matching
  -> supplier payment
  -> close
```

Primary document types:

```text
purchase_request -> supplier_quotation -> supplier_po -> goods_receipt -> supplier_invoice
```

Important notes:

- Purchase orders are generated by QuoteFlow and issued to suppliers.
- Supplier quotations and supplier invoices are usually uploaded supplier files.
- Goods receipt records evidence of delivered goods or accepted services.
- Supplier invoice payment should only be allowed after invoice verification and matching.

## HTTP/request architecture

The app should remain synchronous.

Preferred request pattern:

```text
GET page
  -> Controller loads Eloquent models
  -> Blade renders page

POST form/action
  -> Controller validates request
  -> Service evaluates business rule if needed
  -> Database transaction updates models
  -> Audit event is recorded
  -> Redirect back/show page with status message
```

Avoid making normal workflow actions depend on background jobs.

## Business-rule placement

Current code has many business rules in `DocumentController` and `Document`.

Future changes should gradually move complex rules into service classes.

Good candidates:

```text
app/Services/Documents/DocumentWorkflowService.php
app/Services/Documents/PaymentEligibilityService.php
app/Services/Documents/DirectExceptionPolicy.php
app/Services/Invoices/SupplierInvoiceVerificationService.php
app/Services/Invoices/SupplierInvoiceMatchingService.php
app/Services/Documents/DocumentChainService.php
```

Controllers should orchestrate. Services should decide.

Example:

```text
DocumentController::transition()
  -> DocumentWorkflowService::canTransition($document, $action)
  -> DocumentWorkflowService::transition($document, $action, $user, $payload)
```

## Approval architecture

Current model:

```text
Document draft/rejected
  -> submit
  -> status pending_approval
  -> Approval row created
  -> approve/reject by admin/manager
  -> Document status approved/rejected
```

Document-type approval policy:

Approval policy is document-type-aware:

```text
quotation approval before issue
purchase request approval after supplier quote evidence, or an explicit quote exception
supplier PO approval before issue
supplier invoice verification/matching before payment
```

Purchase request quote evidence rule:

```text
purchase request draft
  -> attach supplier quotation PDF/image on the purchase request
  -> QuoteFlow runs bounded OCR-assisted capture when available
  -> user verifies/corrects the supplier quote fields beside the uploaded source
  -> approver reviews the verified quote evidence before approval
  -> approved request can prefill supplier quotation or purchase order work
```

If no supplier quote is available, the request must use `quote_exception` with a reason. The approver must add a comment when approving that exception. A purchase request must not be approved merely from internal request text when supplier quotation evidence is expected.

## Attachment architecture

Attachments are stored locally and served through authenticated routes.

Pattern:

```text
upload file
  -> store under storage/app/attachments/{document_id}
  -> create Attachment record
  -> preview/download via controller route
```

Do not require public storage symlink or S3 for core workflow.

## OCR and invoice verification architecture

Current business document capture service:

```text
App\Services\Documents\BusinessDocumentCaptureService
```

This is a first-class QuoteFlow service, not an external plugin/provider boundary. It uses local extraction mechanisms embedded in the Laravel workflow:

- Tesseract command
- Symfony Process / proc_open
- optional Poppler `pdftotext` command for PDFs that already contain a text layer
- Imagick for PDF-to-image conversion
- local temp files
- optional embedded PaddleOCR analyzer only when the shared-hosting runtime has been explicitly verified

Architecture rule:

OCR is an assistant, not the source of truth.

Correct target:

```text
Supplier invoice approval requires verified invoice details.
Verification can be OCR-assisted or manual.
```

Do not make successful OCR the only approval path.

External received-document capture should follow the same product logic wherever it reduces retyping:

```text
Supplier/customer sends PDF or image
  -> QuoteFlow creates an OCR-assisted draft when local OCR is available
  -> user reviews and corrects the draft beside the source file
  -> verified values update the structured document record
  -> downstream workflow reuses the verified data
```

Good candidates:

```text
supplier_quotation: quote no., quote date, validity, terms, line items, total
customer_po: customer PO no., PO date, linked quotation reference, line items, total
goods_receipt evidence: delivery/order evidence no., delivered date, received quantities
supplier_invoice: invoice no., invoice date, PO/receipt reference, line items, total
payment proof: payment date, amount, bank/reference no., invoice references
```

Do not apply OCR to internally generated records by default. Customer quotations, purchase requests, supplier purchase orders, and customer invoices should already be structured data in QuoteFlow. The exception is an external supplier quotation file attached to a purchase request; OCR is applied to that uploaded quote evidence, not to the internal purchase request form itself.

OCR must remain an assistant:

- local extraction only, no mandatory external OCR API
- bounded synchronous extraction for reasonable file sizes
- manual verification/editing remains available when OCR fails
- user verification, not OCR, is the trusted business event
- verified external-document capture should record an audit event
- do not add a plugin/provider switching layer for core capture; the document-type parsing and confidence policy belong inside QuoteFlow service classes

PaddleOCR production boundary:

- QuoteFlow may keep an embedded PaddleOCR 3.5.0 analyzer behind `BusinessDocumentCaptureService`.
- PaddleOCR must be disabled by default for Exabytes/Plesk until the real hosting account proves `python3`, PaddleOCR, PaddlePaddle, model/cache paths, and process limits are usable.
- PaddleOCR paths must be environment-configured and remain inside the hosting account, such as `/home/rctech.my/` or `/tmp/`; never hardcode Laragon, Windows, or developer-machine paths for production.
- PaddleOCR failure must degrade to PDF text extraction, local Tesseract where available, and manual verification.
- The trusted business event remains the user's verification/correction, not the OCR engine output.

Business document extraction must prefer a resilient assisted-capture pipeline, not a single brittle OCR pass:

```text
PDF/image uploaded
  -> if PDF has a text layer, try bounded pdftotext layout/plain extraction
  -> if the text-layer result is incomplete, run bounded Tesseract passes with configured page segmentation modes
  -> if enabled and hosting-verified, include a bounded PaddleOCR candidate
  -> parse each candidate by document type
  -> score candidates by supplier/customer name, document number, date, total, terms, line count, and line-total math
  -> show the best draft beside the source file
  -> user verifies/corrects before QuoteFlow trusts the data
```

Do not promise that OCR alone can perfectly read every supplier/customer layout. The product guarantee is that uploads remain usable and reviewable, extraction uses multiple bounded strategies, weak drafts can be corrected, and manual verification remains a first-class path.

OCR-assisted page standard:

```text
Uploaded supplier/customer PDF or image
  -> local OCR/text extraction creates an untrusted draft
  -> document show page treats verification as the active task
  -> extracted fields, line items, terms, and notes are shown once as editable review data
  -> user can include or exclude extracted lines that should become structured document items
  -> source PDF/image stays readable beside or near the capture task
  -> user verifies/corrects the evidence
  -> verified values update the structured document record and audit trail
```

Until verification is complete, do not present OCR values as final document truth. Temporary placeholder document items may exist only to satisfy current validation, and must be replaced by verified included/selected captured line items when the user verifies the evidence.

All OCR scanning pages should avoid duplicate evidence blocks. If terms, delivery, validity, or supplier remarks were extracted, they belong in the assisted capture review state, not repeated again in generic commercial notes or summary cards unless a later workflow needs that verified data.

## Payment architecture

Payments belong to documents.

Payment direction:

```text
outgoing/customer document -> incoming payment
incoming/supplier document -> outgoing payment
```

Payment should update invoice status:

```text
no payment -> issued/matched/etc.
partial payment -> part_paid
fully paid -> paid
close after paid
```

Important target:

Payment eligibility is enforced server-side through `App\Services\Documents\PaymentEligibilityService`.

Current rules:

```text
customer_invoice: issued or part_paid
supplier_invoice: matched or part_paid
```

## Matching architecture

Supplier invoice matching is a business rule layer, not just a status button.

Current matching service:

```text
SupplierInvoiceMatchingService
  -> checks invoice verification
  -> checks related PO/GR or direct exception
  -> checks supplier consistency
  -> checks duplicate supplier invoice number
  -> checks amount/tolerance
  -> returns checklist result
```

The UI should show the checklist result before allowing `matched`.

## Reporting architecture

Reports and CSV exports should remain shared-hosting safe. Report pages can present finance action surfaces, but their backend data must stay bounded and aggregate-based.

Use:

- paginated database queries
- streamed CSV downloads
- chunked export where needed
- SQL aggregates / subqueries for balances, counts, and aging buckets
- limited open-balance lists for action tables

Avoid:

- loading all records into memory
- calculating balances through per-row relationship queries in Blade
- external BI/search engines as required dependencies

## PDF architecture

PDF generation uses DomPDF and Blade views.

Keep PDFs simple:

- A4 business documents
- local assets only where possible
- no JavaScript rendering dependency
- avoid huge images
- compact generated business documents should not create blank trailing pages in preview or download

Do not require headless Chrome/Puppeteer on production shared hosting.

## Data integrity principles

When modifying workflow logic, preserve these principles:

1. A page action must match a backend rule.
2. A backend workflow action must be visible or intentionally restricted.
3. Direct exception paths require explanation/audit.
4. Payment cannot precede invoice readiness.
5. Supplier invoice approval cannot depend only on OCR success.
6. Matching should mean business checks passed.
7. Closed/cancelled documents should not be casually editable.
8. Every important workflow mutation should record an audit event.

## Architecture boundaries for Codex

Codex should not convert the app to:

- API-first SPA
- microservices
- queue-worker-dependent workflow
- Redis/Horizon-dependent system
- VPS-only deployment
- Node-built production runtime

Codex should preserve:

- Laravel monolith
- Blade UI
- Eloquent/MySQL
- local storage
- DomPDF
- synchronous request flow
- shared-hosting deployability

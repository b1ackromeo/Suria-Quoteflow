# QuoteFlow Component Guidelines

## Component strategy

QuoteFlow should use a small, consistent set of components rather than one-off screen-specific styling.

The current CSS already has useful foundations:

- `.btn`
- `.btn-primary`
- `.btn-secondary`
- `.btn-danger`
- `.panel`
- `.metric-card`
- `.workflow-card`
- `.status-chip`
- `.document-list-row`
- `.document-side-card`
- `.studio-section`
- `.source-choice-card`

Future UI work should extend the system carefully instead of creating unrelated visual patterns.

## Card hierarchy

Use three visual levels.

### Level 1: Action or blocker card

Use for next action, blockers, approval required, OCR failed, matching failed, payment locked.

Characteristics:

- stronger heading
- clear CTA
- concise copy
- optional colored left border or icon
- visually above normal information cards

Example:

```text
Supplier invoice not ready
Verify invoice number and total before submitting for approval.
[Verify invoice details]
```

### Level 2: Information card

Use for document facts, financial summary, related records, selected source, and current status.

Characteristics:

- normal white card
- border
- moderate spacing
- low shadow
- clear title

### Level 3: Reference/history section

Use for line items, notes, old attachments, payment history, approval history, audit trail.

Characteristics:

- collapsed by default when not urgent
- minimal shadow
- compact table/list
- no primary CTA

## Button rules

Each screen area should have one primary action whenever possible.

Primary button examples:

```text
Submit for approval
Verify invoice details
Approve
Issue invoice
Mark matched
Record payment
Close document
```

Secondary button examples:

```text
Preview PDF
Download PDF
Edit
Back
Upload
```

Danger button examples:

```text
Reject
Cancel document
```

Rules:

- Do not place multiple primary buttons next to each other unless the user is choosing between mutually exclusive next steps.
- Dangerous actions must have confirmation and a reason when they affect workflow state.
- Buttons must not appear if the backend would reject the action.

## Checklist component

Use checklists for workflow readiness.

Checklist states:

```text
passed
failed
warning
not_applicable
locked
```

Checklist examples:

```text
✓ Invoice copy uploaded
✓ Supplier selected
○ Invoice number not verified
○ Total not verified
Locked: Payment requires matched invoice
```

Do not hide blockers inside validation errors only.

## Status chips

Status chips must be semantic and text-first. Color supports meaning; it does not replace text.

Each chip should map to a state group from `04_status_and_workflow_language.md`.

## Empty states

Every empty state should include:

1. clear title
2. short explanation
3. next action when available

Example:

```text
No supplier invoices yet
Record the supplier invoice, upload the invoice file, then verify and match it before payment.
[Record supplier invoice]
```

## Tables

Tables are for comparison and scan-heavy data.

Rules:

- keep key action in the first or last column
- use status chips consistently
- align money to the right
- use pagination for long lists
- avoid hiding the only action inside row hover

## Forms

Form components should use:

- visible label
- short helper text only when necessary
- inline validation message near the field
- clear required/optional indication where ambiguity exists

Avoid long paragraphs above every field.

## Source choice cards

Source choice cards are a strong pattern and should be preserved.

Rules:

- title must be short
- copy must explain when to use it
- exception paths must mention reason requirement
- selected state must be obvious

Example:

```text
Direct supplier invoice
Use only when no PO or receipt is required. Add a reason.
```

## Preview components

Document previews should answer:

- what file/output is being previewed
- whether it is generated by QuoteFlow or uploaded by a user
- whether preview is unavailable and why
- what action creates or uploads the preview

## Modal/drawer rule

Prefer inline panels and disclosures for shared-hosting-safe Blade flows.

Use modal/drawer only when it reduces navigation or prevents accidental destructive action.

## Anti-patterns

Avoid:

- multiple unrelated cards with equal visual weight
- primary buttons inside history sections
- tiny text for important instructions
- icon-only controls without accessible names
- action labels that describe implementation rather than user goal
